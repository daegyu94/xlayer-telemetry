# Live Dashboard UX Validation

2026-10-03의 `main` (`e1c20ce`)을 기준으로 독립 Prometheus·Grafana 12.1.0·Loki·Alloy와 live demo를 실행했습니다.
Headless Chrome에서 실제 filter·data link·row·browser back을 사용했으며 아래 스크린샷은 synthetic 데이터입니다.
기존 monitoring 서비스와 3FS container는 변경하지 않았습니다.

## 먼저 고칠 5가지와 반영 결과

| 우선순위·화면 | 재현 순서와 영향 | 수정·검증 |
| --- | --- | --- |
| P1 · Timeline identity | Resource node=All → Host row. CPU legend가 `/`로 반복돼 node를 구분할 수 없음. Network/disk도 `sum by(instance)`가 cluster/node를 제거함 | 집계에 cluster·nodename·instance 유지. Node total legend에서 제거된 device 항목 삭제. 실제 CPU/network 화면에서 node 이름 확인 |
| P1 · Policy lag unit | Stage → Weight sync and policy lag. `lag rollout-0`이 `2 s`로 표시됨 | Lag에 별도 `versions` unit과 오른쪽 축 적용. Sync duration은 초 유지. 화면에서 `2 versions` 확인 |
| P1 · Hidden active filters | Stage의 실제 Phase selector에서 reward 선택 → View: Overview. Reward만 나오지만 Phase control은 숨겨짐 | 생성된 dashboard의 query에 쓰이는 filter를 노출. 전달된 reward를 화면에서 확인하고 변경 가능 |
| P2 · Filter recovery | 여러 화면을 거친 제한 조건을 풀려면 URL 또는 각 상세 화면을 찾아야 함 | Reset filters 추가. Cluster·Run·log directory·시간 유지, Step·Trace·resource 등 나머지 선택 초기화. Reward만 보이던 화면에서 전체 stage 복구 확인 |
| P2 · Sandbox identity | Overview의 Sandbox node=All. 여러 node의 `local device busy nvme0n1`이 같은 이름으로 반복됨 | Cluster/node를 legend에 포함. Cgroup과 shared device scope는 유지하고 node별 series 식별 확인 |

앞의 세 항목은 데이터 해석/필터 동작 문제이며, 뒤의 두 항목은 investigation 사용성 개선입니다.
UID·metric 이름·datasource·기존 bookmark는 유지했습니다.
새 Prometheus label이나 collector는 추가하지 않았습니다.

## 결측·부분 수집·stale

Loki/Alloy를 연결하기 전에는 resource metric이 들어와도 Step·candidate·span은 비었습니다.
Collector role을 시작한 뒤 같은 fixture가 Step 목록·diagnosis·span·log에 나타났습니다.
존재하지 않는 Run을 선택하면 application은 N/A이고 shared resource는 별도 관측으로 남습니다.

추가 검증 source에 1000초 오래된 application/GPU timestamp를 넣었습니다.
Scrape는 Up이지만 age가 빨간 `16.7 mins`로 나타나 연결 성공과 freshness가 구분됐습니다.
불량 scrape 응답은 Down·N/A로 나타났습니다.
이 source는 검증용으로만 실행했으며 production collector를 변경하지 않았습니다.

## 검증 결과와 한계

수정 전 새 regression test 5개가 모두 실패했고 수정 후 통과했습니다.
전체 pytest는 promtool을 포함해 **784 passed**였으며 strict Sphinx build도 통과했습니다.
브라우저에서 plugin/datasource rendering 오류는 발견되지 않았습니다.
Baseline 클릭은 이전 interval·record로 이동하고 현재 Trace ID를 초기화했으며, candidate 클릭은 현재 interval로 돌아왔습니다.

실제 VERL 학습·GPU/NCCL·3FS I/O·Ollama 추론·physical multi-node·모바일은 이번 검증에서 실행하지 않았습니다.
Color preset 전체 조합, Grafana Explore 및 모든 표 cell의 context menu도 전수 검증하지 않았습니다.
외부 Browser 연결 초기화가 실패해 시스템 Chrome의 독립 headless instance로 검증했습니다.

Multi-node 화면은 공통 시간축을 사용하며 timestamp를 자동 보정하지 않습니다.
운영에서는 producer와 monitoring host의 clock을 동기화하고, clock guard가 `unsafe`·`unknown`이면 cross-node correlation을 보류합니다.
Node별 span duration은 기본적으로 monotonic clock을 사용하므로 wall-clock 차이와 구분합니다.
Scrape-relative offset에는 전송 지연도 포함되므로 임의 보정값으로 쓰지 않습니다.
[Clock alignment 안내](../../monitoring.md#check-clock-alignment-before-diagnosing)를 따르며 이번 전체 테스트에는 clock skew·결측·wall-clock jump 회귀 검증도 포함됩니다.

## 탐색 구조와 남은 개선

Start Here → Run Overview → Duration → Bottleneck Summary → evidence → Timeline → subsystem 구조를 유지하는 것이 적절합니다.
기존 흐름과 3개 View가 이미 있으므로 새 첫 화면이나 dashboard를 추가하지 않았습니다.
첫 화면은 health·freshness·Run 선택에 집중하고, 상세 지표는 기존 subsystem row에서 확인합니다.

- Next · 넓은 diagnosis 표: 긴 metadata와 summary는 horizontal scroll·pagination·Inspect가 필요합니다. 핵심 열과 세부 표시의 추가 분리는 실제 사용 빈도를 보고 검토합니다.
- Next · N/A 이유: 현재 안내와 tooltip은 있지만 endpoint 미설정·query filter 불일치·수집 장애를 모든 panel에서 자동 구분하지는 않습니다. Source health와 연결할 때 provenance를 유지해야 합니다.
- Later · Mobile/고배율: 좁은 desktop에서는 control이 줄바꿈되지만 긴 legend가 잘립니다. Focus 또는 panel View를 쓰며 mobile 검증은 별도로 필요합니다.
